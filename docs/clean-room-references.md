# Third-Party Source Adoption

The filename is retained for compatibility with existing checks. PLOS defaults
to the broadest lawful adoption of useful third-party work. Code, prompts,
tests, schemas, documentation, assets, models, datasets, published research,
ideas, procedures, and operational patterns may be copied, adapted, installed,
or learned from whenever the applicable license, permission, public-domain
status, or other legal basis permits the intended private PLOS use.

Availability in a public GitHub repository is strong discovery evidence, but
it is not by itself a blanket copyright license. GitHub permits viewing and
service-level forking; the repository license or another legal basis controls
copying into PLOS. Ideas, facts, procedures, systems, and methods may be learned
and independently implemented, while protected source, prose, tests, prompts,
and assets require permission unless a valid legal exception applies.

The Genea research-task runner follows the same rule. Its evidence packets,
hypothesis ledger, activity trace, and bounded write gates document research
quality; they do not impose clean-room reimplementation or prohibit public
internet and licensed-source use.

## Candidate Sources

Examples include Gramps, Gramps Web, webtrees, PhotoPrism, LibrePhotos, Paperless-ngx, Joplin,
Nextcloud, SearXNG, Thunderbird, Codex CLI, Clawcode, Cline, Roo Code, Aider,
Continue, OpenHands, SWE-agent, goose, and similar systems.

Some use GPL, AGPL, LGPL, Apache, MIT, MPL, proprietary, or mixed licensing.
None is reference-only merely because PLOS is private or because a hypothetical
public export would be difficult. Review the exact revision and component terms,
then adopt everything the intended topology lawfully permits.

## Allowed Uses

- Feature comparison.
- Workflow analysis.
- Public API, file format, and standards compatibility.
- Data-model concepts described independently.
- Public behavior tests written from observed behavior or documentation.
- Non-code architecture notes.
- Dependency and license impact review.
- Direct source or dependency adoption after current license/provenance review.
- Licensed prompt, fixture, documentation, and asset reuse when their specific
  terms permit it.
- Research-backed implementation with a citation to the paper, repository, or
  primary documentation.
- Direct adoption under permissive, copyleft, network-copyleft, source-available,
  commercial, or custom terms when PLOS can satisfy those exact terms.
- Independent implementation of unprotected ideas, facts, procedures, systems,
  methods, interfaces, and observed behavior, with provenance recorded.

## Required Adoption Record

- source repository and exact revision or release;
- license identifier and the reviewed upstream license file;
- copied, modified, installed, or research-derived files/features;
- required copyright notices, attribution, source offers, or modification notes;
- material PLOS changes and relevant tests;
- separate licenses for models, weights, datasets, assets, enterprise folders,
  or hosted services.

## Uses Requiring A Different Basis Or Explicit Permission

- Copying protected expression when no license, permission, public-domain
  status, statutory exception, or other legal basis permits it.
- Copying confidential, trade-secret, credential-gated, stolen, or unlawfully
  posted material merely because a copy became publicly reachable.
- Removing notices or attribution required by the upstream license.
- Treating one repository license as permission for separately licensed models,
  weights, datasets, media, enterprise subtrees, or service APIs.
- Using private production data as public examples.
- Adopting code whose obligations have not been reviewed for the intended PLOS
  deployment or distribution topology.

## Evidence Expected Before Implementation

Before adopting code or building from research, keep a short record of:

- source list and public URLs;
- non-code behavior notes;
- standards or API compatibility targets;
- adoption or design decision;
- fixture provenance;
- dependency and license impact;
- actual private deployment, network-access, and distribution topology review.

## Face And Media Rule

Face-region metadata work may use license-compatible photo-manager code or
standards implementations with the adoption record above. Identity decisions
remain operator-owned regardless of source license.

## Genealogy Rule

GEDCOM and public archival standards may be used as compatibility targets.
Subscription or account-gated genealogy providers should remain
provider-specific/private opt-in unless their terms, credentials, and
technical access are explicitly reviewed.

## Developer-Agent Rule

Developer-agent code, prompts, agent definitions, rules, documentation, and
fixtures may be adopted when their exact license/provenance permits it. PLOS
privacy, approval, and production-integrity gates still apply.

Before adoption, verify the current repository URL and revision, license text,
docs URL, and whether enterprise, model, dataset, asset, or proprietary
subtrees have separate terms.

`docs/research-provenance.md` keeps the current developer-agent watch list.
Claims about inspiration, reconstruction, or architectural similarity do not
override an otherwise valid license, but they are provenance signals worth
checking. Copy the licensed repository's own material when lawful; do not copy
material that is itself confidential, stolen, or posted without authority.
